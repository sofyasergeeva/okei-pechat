тарифы A4/A3, ч/б/цвет/фото, нечётный duplex, копии, выбранные страницы, листы,

customer.test.cjs — пять исходных сценариев и восемь граничных проверок:

- Отмена нового заказа сохраняет параметры и историю; заказ в работе не отменяется.
- Ответ сохраняется и переводит attention в review.
- Завершённые заказы исключены из активных.
- Макет сохраняется с JSON, превью и владельцем.
- К1: черновик сохраняет свежие заказы и дополнительные поля старого хранилища.
- К1: конфликт отмены со свежим статусом сотрудника отклоняется.
- К1: изменение одного заказа сохраняет изменения другого.
- К2: отказ оформления PDF сохраняет черновик, комментарий и Blob; повтор создаёт один заказ.
- К2: повтор сохранения макета после отказа не дублирует заказ.
- К3: повторный вход под тем же логином инвалидирует старую операцию.
- К3: выход во время второй записи макета не создаёт заказ без владельца.
- К3: оформление PDF после смены пользователя не меняет новый аккаунт.

critical-regressions.cjs сохраняет исходные проверки правильного поведения:

| Ошибка | Проверка                                                  | Результат |

К1 в Node имитирует уже сохранённое изменение другой вкладки. Для К3 используются
управляемые точки ожидания без случайных задержек.

customer-modules.test.cjs — 6 проверок выделенных утилит, состояния/сессий,

## Изоляция

OrderMath читается с диска и выполняется в node:vm без переписывания кода.
Кабинет тестируется через фактические ES Modules и createCustomer().
Каждый тест получает отдельное состояние, слушатели, JSON и Blob в памяти.
customer-harness.cjs — минимальная имитация DOM/IndexedDB, а не полноценный браузер.

Playwright создаёт отдельный непостоянный BrowserContext на тест. Настоящие профили,
пользовательские localStorage/IndexedDB и storageState не открываются и не очищаются.
Временный сервер работает на 127.0.0.1:18087 и останавливается Playwright.
Занятый порт считается ошибкой; пользовательский сервер не переиспользуется.

## Браузерные smoke-тесты

Конфигурация: playwright.config.cjs. Сценарии: tests/browser.smoke.cjs.
Использование установленного Edge поддерживается
[документацией Playwright](https://playwright.dev/docs/browsers#google-chrome--microsoft-edge).

1. Главная, обе темы, сохранение темы после перезагрузки, отсутствие pageerror.
2. Вход заказчика и сотрудника через существующую форму.
3. Реальный sample.pdf: три страницы, 12 ₽ и оформление. Во второй вкладке
   сотрудник принимает заказ, отмечает готовность и пишет сообщение.
   Заказчик сохраняет профиль и видит актуальные статус и сообщение.
4. Отказ записи только в тестовой странице: нет успеха, комментарий сохраняется,
   после восстановления записи оформление проходит.
5. Конструктор: текст спереди и сзади, превью обеих сторон и оформление.
6. Ширина 390 px: главная, печать, диалог сотрудника, отсутствие горизонтального
   переполнения на проверяемых экранах.
7. Старая схема localStorage/IndexedDB: сохранённые PDF, профиль, черновик,
   статус и переписка доступны после перезагрузки и повторного входа;
   дополнительные поля JSON сохраняются. PDF открывается из прежнего Blob.
8. Canvas: клавиатура и pointer-перенос, пропорции, порядок слоёв, восстановление
   черновика после перезагрузки, реальный PNG 2400×3368 с прозрачным фоном и принтом.
   Координаты pointer проверяются с учётом округления Edge, подтверждённого на исходнике.
9. Регистрация: несовпадение паролей, создание аккаунта, повторный вход в памяти
   страницы, запоминание логина и темы. После перезагрузки временный аккаунт исчезает.
10. Сотрудник: проверка файла, готовность, обязательное подтверждение оплаты,
    сохранение выдачи, отчёт по группам и фактическое скачивание CSV.

Во всех сценариях отслеживаются pageerror и console.error, включая новые вкладки.

## Оставшиеся ограничения

- Read/merge/write в localStorage не является транзакцией: между чтением и записью
  остаётся узкое окно одновременной записи из нескольких вкладок.
- Ключи okei-customer-v1:<логин> и существующие данные сохранены; удаления и
  миграции пользовательских данных нет.
- После отмены операции могут остаться Blob без ссылки из заказа. Автоматической
  очистки файлов пока нет.
- Авторизация и роли остаются демонстрационными, удалённой базы нет.
- Полная валидация повреждённого хранилища и неизвестных значений бумаги/переплёта
  не входит в этот этап.
- Все устройства, браузеры, доступность, экспорт и Canvas-геометрия не покрыты
  десятью браузерными сценариями.

Кабинеты, конструктор и оболочка разделены на модули. Карта зависимостей и места
добавления функций описаны в docs/architecture.md. Следующие изменения также
требуют npm test и npm run test:e2e.


## Серверные проверки

```powershell
npm.cmd run test:server
# Только новые браузерные сценарии:
node_modules/.bin/playwright.cmd test server.browser.cjs
```

server.test.cjs содержит 11 содержательных проверок фактического API и клиента:

1. Регистрация, вход/выход, HttpOnly-cookie, хеш пароля, запрет роли staff при регистрации,
   пересчёт цены/страниц на сервере, запрет доступа к чужому заказу и PDF, Origin.
2. Две независимые сессии: заказ, уточнение, ответ, проверка, готовность, оплаченная выдача,
   HTTP 409 на устаревшую версию; закрытие/повторное открытие HTTP и SQLite сохраняет данные.
3. SQLite-триггер искусственно запрещает запись события: откатываются и заказ, и история;
   после удаления тестового триггера повтор создаёт ровно один заказ.
4. Поддельный PDF, неверные параметры/диапазон/копии и превышение лимита входа отклоняются.
5. Запоздалый ответ API после invalidate() отклоняется, не передаётся новому аккаунту.
6. Отмена нового заказа, неправильное тело запроса, отзыв и истечение сессии.
7. Остановка процесса Node и запуск нового server/index.cjs: аккаунт, cookie-сессия,
   параметры/цена/история заказа и реальные байты PDF остаются доступны.

Все серверные тесты создают собственный каталог в OS temp. Тестовый триггер действует только
в этой временной базе. Очистка проверяет родительский каталог и префикс перед удалением.
Реальные var/okei, localStorage и IndexedDB пользователя не открываются.

server.browser.cjs содержит четыре сценария Edge (два дополнительных описаны ниже):

- Регистрация заказчика, PDF-заказ, вход сотрудника в другом контексте, общая очередь,
  уточнение/ответ, мобильный инспектор сотрудника, готовность/выдача, история заказчика,
  сохранение сессии после reload, выход/повторный вход и обе темы.
- HTTP 500 при оформлении не показывает успех и сохраняет черновик; повтор создаёт один
  PDF-заказ. Конструктор оформляет серверный мерч в общей очереди; новые локальные заказы не создаются. Проверяется мобильный экран 390×844.

server-fixture.cjs запускает отдельный API на 18088 с временными БД/файлами и только тестовым
сотрудником. Исходные 10 браузерных тестов используют прежний статический сервер 18087.
Два контекста имеют раздельные cookie/localStorage/IndexedDB. Два физических устройства и
работа через внешнюю сеть на этом этапе не проверялись.

заказа, повторную отмену без нового события, запрет customer на начало печати и гонку двух HTTP

ошибку чтения дерева страниц (исправленная прежняя ошибка).

## Серверный мерч и polling

Два Node-сценария проверяют цену, доступ к PNG/JSON, параметры и повреждённые/неполные пакеты,
атомарный откат при отказе SQL, отмену до изготовления, запрет после него, переписку и повторное
открытие сервера с сохранёнными байтами вложений. Миграция проверяет v1 и v2 со старым заказом.
Отдельный тест API/polling с mock timers проверяет единое чтение очереди, видимость вкладки,
отсутствие перекрывающихся обновлений, восстановление после ошибки и остановку.

Четвёртый серверный сценарий Edge оформляет мерч через настоящий Canvas, скачивает сотрудником
из другого контекста JSON, превью и обе стороны PNG; проверяет размеры, прозрачность и наличие
принта. Сообщения/статусы приходят через polling без reload; черновики переписки обеих ролей,
несохранённый профиль, DOM-узлы полей, фокус и выделение сохраняются. Проверены восстановление
после ошибки сети и отсутствие чтений после выхода. Часы ускорены browser.clock только в тесте.

Для текущего MVP сравнены 12 экранов с dac0079 в отдельных временных копиях, при одинаковых
темах, данных, времени и разрешениях. HTML совпал на всех 12 после нормализации UUID;
9 PNG совпали попиксельно. В обоих кабинетах заказчика отличаются по 2 пикселя, у сотрудника —
9, максимум 1/255 на канал. Эталоны не перезаписывались. Артефакты — OS temp,
okei-mvp-visual-4bf473834cf74cd1bf7dc95b2822984b/visual. Серверная карточка мерча — новый
сценарий, готового прежнего серверного эталона для неё нет; скриншот проверяется отдельно.
