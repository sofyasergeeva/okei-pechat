# Автоматические проверки ОКЭИ ПЕЧАТЬ

## Запуск

Из корня проекта в PowerShell:

```powershell
npm.cmd test
npm.cmd run test:regressions
```

Без npm:

```powershell
node --test tests/order-math.test.cjs tests/customer.test.cjs
node --test tests/critical-regressions.cjs
```

Основной набор: **19 успешных тестов**, код завершения 0.
Отдельные регрессии: **3 падающих теста**, код завершения 1, пока К1–К3 не исправлены.
Обязательная проверка — только `npm.cmd test`. Она явно перечисляет основные файлы
и не запускает регрессии. После исправления каждой ошибки соответствующий тест
нужно перенести в основной набор без ослабления проверок.

## Воспроизводимые К1–К3

В `critical-regressions.cjs` проверяется правильное ожидаемое поведение.
Здесь нет инвертированных проверок, `skip` или `todo`.

| Ошибка | Воспроизведение | Правильный результат | Текущий результат |
| --- | --- | --- | --- |
| К1 | После загрузки кабинета другая вкладка сохраняет ready и сообщение сотрудника; заказчик сохраняет профиль | Статус и сообщение сохраняются | Снова work, сообщения пусты: FAIL |
| К2 | IndexedDB принимает макет, но localStorage отклоняет запись заказа | Нет подтверждения успешного оформления | Открывается окно успеха: FAIL |
| К3 | Запись макета Alice приостановлена; выполнен вход Bob; запись продолжена | У Bob нет заказа Alice | У Bob появляется один заказ: FAIL |

К1 имитирует уже сохранённое изменение другой вкладки непосредственно в общем
тестовом хранилище; интерфейс сотрудника в этом тесте не выполняется.
Для К3 используется управляемая точка ожидания, а не задержка `setTimeout`.
После будущего исправления допустимы как сохранение за исходным владельцем,
так и отмена операции старой сессии; запись в аккаунт Bob недопустима.

## Изоляция и ограничения

- Исходники загружаются с диска и выполняются в `node:vm` без переписывания кода.
- Для каждого теста заказчика создаются отдельные VM, слушатели событий,
  localStorage и файловое хранилище в памяти.
- `customer-harness.cjs` содержит только тестовые данные и минимальные имитации
  DOM/IndexedDB. Это не полноценный браузер и не проверка реализации IndexedDB.
- Настоящие профили Chrome/Edge и пользовательские хранилища не открываются.
- В позитивном тесте PNG-превью — Blob-маркер. Декодирование изображения,
  Canvas, PDF.js и загрузка реального PDF здесь не проверяются.
- Авторизация из `app.js`, работа интерфейса сотрудника, доступность, геометрия
  вёрстки и визуальная регрессия требуют браузерных проверок.

## Минимальный браузерный этап

На проверенной Windows найдены Google Chrome и Microsoft Edge. Playwright не
установлен. Для следующего этапа нужна devDependency `@playwright/test`; сейчас
она не устанавливалась. После согласования установки выбрать установленный Edge
через `channel: 'msedge'`. Отдельную загрузку браузеров не запускать.
Это поддерживается [официальной документацией Playwright](https://playwright.dev/docs/browsers#google-chrome--microsoft-edge).
Фактический запуск через Playwright пока не проверен.

Для каждого теста использовать новый непостоянный BrowserContext. Не передавать
реальный `userDataDir`, не импортировать пользовательский `storageState`, не
очищать реальный localStorage/IndexedDB. Локальный сервер запускать отдельным
процессом на свободном порту с автоматической остановкой после набора.

| Сценарий | Основные проверки |
| --- | --- |
| Главная | Заголовок, кнопки, локальные ресурсы, отсутствие ошибок консоли |
| Вход обеих ролей | student_23 и staff_01 с тестовым паролем okei2026, правильный кабинет, неверный пароль |
| PDF-заказ | Загрузить dist/assets/sample.pdf, проверить 3 страницы и 12 ₽ для A4 ч/б; оформить и проверить историю после повторного входа |
| Работа сотрудника | В том же BrowserContext войти сотрудником, найти созданный заказ, отметить проверку, принять в работу и отметить готовность |
| Просмотр заказчиком | Войти снова заказчиком, проверить ready, параметры и историю событий |
| Конструктор | Пресет, текст, обе стороны, перемещение, превью, экспорт и сохранённый заказ |
| Темы | Переключение sky/glass и сохранение выбора после перезагрузки |
| Мобильная версия | 390×844: навигация, мастер печати, диалог сотрудника, конструктор, отсутствие горизонтального переполнения |

Последовательная смена ролей в одном контексте проверяет рабочий сквозной сценарий.
Две одновременно открытые вкладки и конкурентные изменения добавить отдельными
браузерными регрессиями К1–К3, не подменяя ими существующие тесты в памяти.

## Эталонные скриншоты

После установки Playwright создать утверждаемые вручную эталоны текущего дизайна:
главная, вход, кабинет заказчика, параметры PDF, очередь сотрудника и конструктор.
Для каждого экрана — sky/glass, desktop 1440×1000 и mobile 390×844.

- Фиксировать Windows, версию браузера, deviceScaleFactor 1, locale ru-RU,
  timezone Asia/Yekaterinburg, время и одинаковый набор тестовых данных.
- Дожидаться загрузки шрифтов, изображений и готовности Canvas; использовать
  одинаковую гарнитуру, не смешивать эталоны с fallback-шрифтом.
- Для статичных снимков фиксировать фазу анимации средствами тестового окружения;
  движение и переходы проверять отдельно с включёнными анимациями.
- Не менять CSS, HTML или анимации приложения ради стабильности снимков.
- Хранить утверждённые эталоны в tests/browser/snapshots/, фактические снимки и
  различия — в уже игнорируемом test-results/.
- Существующие docs/*.jpg не считать автоматическими эталонами: условия их
  получения не зафиксированы. Обновлять новые эталоны только после просмотра diff.

Браузерные тесты и эталонные снимки на этом этапе не создавались и не запускались.
