Создано 16 новых модулей: 5 для сотрудника, 6 для конструктора и 5 для оболочки.
Один файл объединяет связанные функции; отдельных файлов для каждого действия нет.
Большой объём views.mjs — статическая разметка, разделённая на смысловые функции.
Конкатенация строк сохраняет исходные пробелы в HTML.

## Зависимости и инициализация

index.html подключает ui.js, OrderMath и living.js, затем app.js как ES Module.
Controls остаётся классическим скриптом с явной инициализацией после оболочки.
Модульный граф загружается до выполнения app.js. Динамическая вставка app.js больше
не нужна; initializeStudio/initializeStaff удалены. Порядок создания компонентов:
Studio → Customer → Staff → оболочка → Controls. Регистрация обработчиков сохраняет
этот порядок. Публичные window.Studio, window.Customer, window.Staff и entryToast
сохранены для совместимости; реальные зависимости передаются функциями и объектами.

createCustomer получает window/document, storage/indexedDB, OrderMath, UI, Studio
и уведомления. createStaff получает браузерные API, хранилища и UI. createStudio
получает document/indexedDB, уведомления и функцию оформления заказа в Customer;
его контроллер не обращается напрямую к window.Customer. startApp получает оба
кабинета, UI и браузерные API, выбирает интерфейс по действующей роли.

Модули данных не формируют DOM; шаблоны не записывают данные. Статусы сотрудника,
учёт оплаты, пауза/возобновление, агрегаты отчёта и CSV отделены от обработчиков.
Геометрия конструктора не зависит от DOM: преобразование координат принимает
прямоугольник Canvas; формулы переноса, размеров, поворота и ограничения перенесены
без изменения. Рисование, порядок слоёв, clipping, счётчик отрисовок и экспорт
сохранены. Контроллер связывает сохранение с обновлением панелей и подтверждением.

Дубли форматирования/экранирования/ID используют shared.mjs. Скачивание CSV и PNG
объединено в downloadBlob с прежними параметрами: добавление ссылки в DOM и отзыв
URL через 60 секунд для сотрудника; 15 секунд без добавления ссылки для конструктора.
Пустой макет и геометрия теперь имеют один источник в studio/model.mjs; правила
сотрудника используются обработчиками и проверяются непосредственно в Node.

## Хранилища и запуск

Сайт запускается по HTTP: `npm.cmd start`, http://127.0.0.1:8080.
Локальный сервер отдаёт .mjs с JavaScript MIME-типом; сборщик не нужен.
Будущий статический хостинг должен также обслуживать ES Modules по HTTP.

Сохранены ключи okei-customer-v1:<логин>, okei-staff-demo-v1, okei-concept-login
и okei-preferred-theme; базы okei-customer-files/files и okei-studio/designs,
обе версии 1. Миграций, очистки и чтения реального пользовательского профиля нет.
К1–К3 остаются в обязательных тестах: слияние и контроль конфликтов, проверка результата
записи до сообщения об успехе, контроль владельца и версии сессии после ожиданий.
Сохранение макета по-прежнему последовательно записывает снимок с захваченным владельцем.
Авторизация и регистрация остаются демонстрационными: аккаунт регистрации живёт
в памяти страницы; запоминается только логин. Перезагрузка требует нового входа.

## Оставшиеся ограничения локального режима

localStorage не обеспечивает транзакцию между вкладками; прежнее окно конкурентной
записи сохраняется. Для повреждённых сохранений нет полной проверки схемы. После
прерванных операций могут оставаться Blob без ссылок. Авторизация и роли остаются
локальной демонстрацией в режиме без ?mode=server. Серверный сценарий описан ниже.

Manrope обслуживается локально: исходные WOFF2 Google Fonts v20, веса 400/500/600/650/700/750/800,
те же unicode-range и font-display. dist/style.css меняет только URL @import; файлы и OFL.txt
находятся в dist/assets/fonts. Лицензия: https://github.com/google/fonts/blob/main/ofl/manrope/OFL.txt. Пользовательские действия из информационных
диалогов направляют в существующие PDF-мастер и коллекцию.
Покрытие Canvas не исчерпывает все сочетания шрифтов, изображений и поворотов; при
развитии движка следует расширять целевые проверки, сохраняя существующие формулы.

## Серверные PDF- и мерч-заказы

Статический npm start сохраняет деморежим; ?mode=server выбирает API явно.
API-сервер по умолчанию помечает HTML data-mode=server (SERVER_ONLY=true), а production
всегда делает это для / и /index.html, независимо от query. Демо-логины в API не действуют. В серверном режиме app/forms.mjs
использует API для авторизации, а оболочка получает прежние интерфейсы render/home/reset.
Шаблоны customer/views.mjs и staff/views.mjs переиспользуются; Вёрстка и графика сохранены; CSS меняет только импорт локального шрифта.

```text
server/
  index.cjs   — конфигурация окружения, HTTP, завершение процесса
  app.cjs     — маршруты Express, Origin/Host, загрузки, приватная выдача вложений, ошибки
  auth.cjs    — scrypt, пользователи, SQLite-сессии, cookies и ограничение попыток
  db.cjs      — SQLite-схема, ограничения, индексы, WAL и внешние ключи
  orders.cjs  — проверка PDF/параметров, исходный OrderMath, права, транзакции и версии
  merch.cjs   — проверки JSON/PNG конструктора, параметров и существующей цены мерча
  limits.cjs  — квоты хранилища/заказов/аккаунтов и допуск загрузок
  backup.cjs  — WAL-снимок, файлы, контроль целостности, восстановление в новый каталог
  manage.cjs  — создание сотрудника, резервная копия и восстановление оператором
dist/
  api.mjs             — fetch с cookie, поколение сессии, единое чтение очереди, polling и точечное обновление DOM
  server-customer.mjs — серверные PDF/мерч, существующие шаблоны и конструктор
  server-staff.mjs    — серверная очередь, статусы, переписка и отчёт
```

API одного origin (JSON, кроме загрузки и скачивания):

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | /healthz | Готовность процесса и SQLite, без пользовательских данных |
| POST | /api/auth/register | Создать только заказчика, открыть сессию |
| POST | /api/auth/login | Проверить пароль, открыть сессию |
| GET | /api/auth/session | Восстановить текущего пользователя или null |
| POST | /api/auth/logout | Отозвать текущую сессию |
| PATCH | /api/profile | Обновить имя/группу текущего заказчика |
| POST | /api/files | multipart file (старый одиночный) или files (1–10 PDF), пакет сохраняется целиком |
| GET | /api/files/:id | Вложение владельцу; сотруднику — после создания заказа |
| GET / POST | /api/orders | Очередь по роли / PDF (JSON) или мерч (multipart) |
| GET | /api/orders/:id | Прочитать доступный заказ |
| GET | /api/orders/:id/file | Прежний маршрут: первый/единственный PDF |
| GET | /api/orders/:id/files/:fileId | Открыть/скачать конкретное вложение доступного заказа |
| POST | /api/orders/:id/printing | Сотрудник начинает печать/изготовление в work, с version |
| PATCH | /api/orders/:id/status | Разрешённый переход с version |
| POST | /api/orders/:id/messages | Сообщение с version, сотруднику доступен pause |
| POST | /api/orders/:id/read | Сбросить собственный счётчик непрочитанного |

users, sessions, files, orders, order_files, events и messages связаны внешними ключами.
order_files хранит порядок вложений и отдельные снимки params/quote каждого PDF. orders.file_id
сохранён как первый файл для совместимости прежнего API. POST /api/orders принимает fileKeys,
старый fileKey также поддерживается. Проверяются уникальность/число ID, владелец каждого файла,
общий размер и параметры каждого документа; создание заказа, связей и истории атомарно.
Пакетная загрузка сначала проверяет все PDF, затем пишет новые UUID-файлы; их метаданные
сохраняются SQL-транзакцией. При отказе записи убираются только файлы этого нового пакета. Заказ не создаётся
по частично сохранённому списку. Непривязанные успешные загрузки остаются приватными.
Общие параметры рассчитываются исходным OrderMath отдельно для каждого PDF, затем суммируются
print/total, страницы, листы, переплёт и экономия. Каждый документ имеет свою последнюю
непарную страницу и переплёт. Физического объединения PDF нет. Заказ хранит снимок
имени/группы, параметров и цены при оформлении. Роль читается из БД по серверной сессии,
владелец — из аутентифицированного запроса. Файлы именуются UUID, путь не задаётся браузером.
PDF проверяется по сигнатуре, размеру и разбору pdf-lib. Количество страниц берётся из PDF.
Цены вычисляются реальным dist/order-math.js в изолированном Node VM без копии тарифов.

SQL-параметры связаны через placeholders. Оформление и каждое изменение заказа используют
транзакцию вместе с историей/сообщением. version отклоняет устаревшую запись с HTTP 409;
клиент обновляет данные и предлагает повторить действие. Новый заказ не добавляется в клиентское
состояние до успешного ответа API. Отзыв сессии инвалидирует запоздалые клиентские ответы.
Пароли с солью и scrypt, в sessions — SHA-256 от случайного токена; данные сессии не доверяются
localStorage. Попытки регистрации/входа ограничены на IP и IP+логин за 15 минут.

Разрешены new/review → work после проверки, work → ready только после явного начала печати,
ready → issued после отметки оплаты; attention → work после согласования. Сообщение сотрудника с pause переводит
new/work/review в attention; ответ заказчика — attention → review. Заказчик отменяет собственный
new/work/attention/review, пока printing_started_at отсутствует; сотрудник указывает причину.
POST printing и отмена проверяют свежие status/version и меняют запись в SQLite-транзакции.
Начало печати не создаёт новый статус: сохраняются printing_started_at и новая version.
Отмена сохраняет cancelled_at и событие cancelled; повтор отмены возвращает тот же результат.
После начала печати отмена запрещена, в том числе при последующем уточнении. Файлы не удаляются.
canCancel в API определяет доступность кнопки. Устаревшее подтверждение отмены при HTTP 409
закрывается после обновления заказа. Итоги оплаты являются отметкой, а не транзакцией банка.

Миграция v1 → v2 добавляет два nullable-времени и order_files, переносит одиночные связи
без пересчёта сохранённой цены. cancelled_at восстанавливается только из существующего события;
неизвестное начало печати старых заказов остаётся NULL. ready/issued не допускают отмены.
Миграция v2 → v3 добавляет тип заказа и вложения. Таблица files перестраивается в SQL-транзакции:
число страниц допускает NULL для JSON/PNG; идентификаторы, владельцы и связи сохраняются.
Проверяется foreign_key_check, при ошибке транзакция откатывается. Старые суммы не пересчитываются.
Повторный запуск безопасен. Версия схемы — PRAGMA user_version=3.

Локальный деморежим отделён; его данные не читаются, не удаляются и не мигрируются в серверные заказы.
Конструктор в серверном режиме сохраняет прежний namespace черновика server-merch:<UUID>.
Новые мерч-заказы используют те же orders/order_files/events/messages, роли и версии, что PDF.
Мерч отправляется полным multipart-пакетом design/preview/front/back: JSON обязателен,
PNG сторон обязателен только для заполненной стороны. Проверки и декодирование PNG выполняются
до записи; файлы с UUID и SQL-записи заказа сохраняются общим механизмом с откатом новых файлов
при ошибке. Начало изготовления использует прежнее поле printing_started_at и правила отмены.
Цена берётся из MERCH_PRICE, палитра — из действующей модели конструктора; данные клиента о цене
не используются. Производственные PNG создаются тем же кодом, что существующий экспорт,
без изменения геометрии. Сервер проверяет структуру и формат, но не перерисовывает JSON
и не доказывает визуальную идентичность присланного PNG макету. Сотрудник проверяет файлы.

Polling с интервалом 27 секунд работает только в активной серверной сессии видимой вкладки.
GET /orders объединяет одновременные чтения и повторяет чтение последовательно, если за время
запроса завершилась собственная запись. Поколение сессии отвергает устаревшие ответы.
Фоновое обновление патчит только данные: формы, Canvas и поля переписки остаются теми же DOM-узлами.
Сохраняются фокус, выделение в полях, раскрытые details и положение прокрутки. Ошибка сети
допускает следующую попытку, HTTP 401 и выход останавливают цикл. Таймаут запроса — 60 секунд.
Тема остаётся прежней настройкой браузера.

Настройки: HOST, PORT, PUBLIC_ORIGIN, DATA_DIR, COOKIE_SECURE; .env.example содержит только
пустые/учебные значения. Node 24.12.0 и better-sqlite3 13.0.3 реально проверены на Windows;
SQLite 3.53.4. Зависимости: Express 5.3.0, multer 2.5.0, pdf-lib 1.17.1, без ORM и сборщика.

Этот этап добавляет квоты, резервное копирование и конфигурацию контейнера. Нет восстановления
пароля, автоматического удаления/архивации и фонового расписания резервных копий. Тарифы
требуют согласования с типографией. Публичное развёртывание не выполнялось.

## Финальная проверка безопасности и эксплуатации

Авторизация использует scrypt, cookie HttpOnly/SameSite=Strict, случайные токены с хешем в SQLite;
при HTTPS/production — Secure и __Host-префикс. Не более 10 сессий на пользователя; старые
сессии отзываются при превышении и все сессии сбрасываются при восстановлении копии.
Изменяющие API требуют точный Origin, API требует Host из PUBLIC_ORIGIN. TRUST_PROXY
по умолчанию выключен: неподтверждённый X-Forwarded-For не меняет IP для лимита входа.
JSON ограничен 32 КиБ, multipart — 51 МиБ с заголовками, суммарные файлы — прежние 50 МиБ.
При chunked-загрузке ограничение проверяется по реально прочитанным байтам; превышение закрывает
соединение. Допуск — две загрузки на процесс и одна на пользователя. Резервирование объёма
защищает квоты от конкурентных загрузок до SQL-коммита. Квоты и значения приведены в README.
Частично записанный новый файл закрывается и удаляется при ошибке; выполняется file.sync перед
фиксацией метаданных. Перед записью проверяется свободное место с резервом 64 МиБ.
Ошибки 500 логируют только код, а ответы не раскрывают пути. При нехватке места — HTTP 507.
DATA_DIR проверяется по реальному пути; symlink в dist и symlink каталога pdf запрещены.
CSP ограничивает ресурсы своим origin; inline styles оставлены для существующих шаблонов и Canvas.
Доступ к заказам, сообщениям и вложениям остаётся через прежние проверки роли/владельца.

Резервная копия использует better-sqlite3.backup (SQLite Online Backup API), а не простое
копирование рабочего .sqlite без WAL: https://sqlite.org/backup.html. Из полученного снимка
читается список всех зарегистрированных файлов; каждый файл неизменяем после SQL-коммита.
Копируются только эти UUID-файлы, проверяются размеры и SHA-256. manifest.json записывается
последним. Непривязанные, но зарегистрированные загрузки тоже сохраняются; .env не копируется.
Остановка записи для снимка не требуется при текущем правиле отсутствия удаления/изменения файлов.
Будущая очистка файлов должна согласовываться с backup, иначе потребуется пауза записи/удаления.
Восстановление разрешено только в новый приватный каталог, проверяет SQLite/FK/хеши и оставляет
RESTORE_INCOMPLETE при отказе копирования. Запуск с таким маркером запрещён. После восстановления
удаляются только sessions в НОВОЙ базе, затем маркер снимается; заказы и вложения не меняются.
Инструкции и команды — в README. Копии нужно хранить отдельно и ограничивать ACL;
автоматическое расписание/ротация и шифрование носителя остаются задачей оператора.

Dockerfile содержит две стадии на закреплённом официальном Node 24 bookworm-slim:
нативные зависимости устанавливаются в Linux с python3/make/g++, финальный образ не содержит
инструментов сборки и devDependencies. COPY ограничен package/server/dist; .dockerignore
не допускает .env, Git, БД, загрузки и копии. USER node, data/backups — отдельные volumes,
read-only корень, /tmp tmpfs, cap_drop/no-new-privileges, лимиты CPU/RAM/PID, init, SIGTERM
с ожиданием запросов и активных async-операций. /healthz используется healthcheck.
Compose не публикует порт вне loopback. После запуска Engine образ реально собран и проверен:
Docker 29.7.2, Linux amd64, Node 24.22.1, SQLite 3.53.4. Native better-sqlite3 загружается,
healthcheck healthy, процесс UID 1000, DATA_DIR 0700, корень read-only, .env в образе нет.
В отдельном Compose-проекте созданы PDF-заказ с двумя вложениями и мерч с JSON/preview/front PNG;
стоимости 40/1900 ₽, роль сотрудника, чужой доступ и переписка проверены. Все пять файлов
сравнены побайтно до/после stop/start и после backup/restore с пересозданием контейнера.
Обычный restart сохраняет сессию, восстановление отказывает старому cookie и допускает новый вход.
Тестовые volumes/network/container удалены только после проверки нового project-prefix и labels;
локальный образ оставлен. Существующие volumes не использовались. Реального HTTPS/TLS-прокси
и внешнего развёртывания не было.

## Пример HTTPS reverse proxy

Пример для nginx на том же сервере; сертификат предоставляет оператор. Не применялся к внешнему
серверу и не заменяет проверку реального TLS, прав сертификата и firewall. В окружении приложения:
NODE_ENV=production, PUBLIC_ORIGIN=https://print.example.org, COOKIE_SECURE=true.
TRUST_PROXY задаёт только действительный адрес nginx: при прямом loopback это 127.0.0.1/32;
для Docker проверь адрес gateway, видимый контейнеру. Не доверяй всем proxy-заголовкам.

```nginx
server {
    listen 443 ssl;
    server_name print.example.org;
    ssl_certificate /etc/tls/fullchain.pem;
    ssl_certificate_key /etc/tls/private.key;
    add_header Strict-Transport-Security "max-age=31536000" always;
    client_max_body_size 51m;
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 130s;
        proxy_request_buffering on;
    }
}
```

PUBLIC_ORIGIN фиксирован и не строится из непроверенных заголовков. Cookie Secure определяется
конфигурацией HTTPS, а не входящим X-Forwarded-Proto. Прокси перезаписывает X-Forwarded-For,
сохраняет Host и завершает TLS; прямой API-порт должен оставаться закрытым снаружи.
Перенаправление HTTP на HTTPS настраивается оператором перед внешним запуском.
